### Unit 4 hardware anomaly: inverted PENIRQ

This unit behaves differently from units 2 and 3 on the touch interrupt line:

| State | units 2 & 3 | unit 4 |
|---|---|---|
| untouched | IRQ **HIGH**, z = 0 | IRQ **LOW**, z = 0 |
| touched | IRQ **LOW**, z ≈ 500–1300 | IRQ **HIGH**, z = 544 |

Raw `tp` diagnostic from this board (untouched → pressed):

```
0  irq=0 z=   0 | rise x=   0 y=4095 | fall x=   0 y=4094     <- idle
80 irq=1 z= 544 | rise x=2331 y=2076 | fall x= 554 y= 104     <- pressed
```

Because `touch_is_down()` used to read that pin's polarity, every tap on this
board registered as a *release*: calibration waited for a press that was already
asserted and discarded the real ones (`BATAL di kotak 1`), and the UI never
responded. The XPT2046 pressure reading itself is perfectly good.

**Fix (2.8" path only, `2.8.2`)**: `touch_is_down()` now derives presence from the
pressure axis (`z >= TOUCH_Z_DOWN`, the same threshold `touch_raw()` validates)
instead of PENIRQ polarity, so presence is independent of how a given board wires
that pin. The change is inside `#if TOUCH_SEPARATE_BUS`; the 3.5" TFT_eSPI branch
is untouched and still uses `getTouchRawZ() > 300`.

### Flashing incident (recovered)

The first attempt to flash `2.8.2` aborted during the 1.2 MB app write
(`PermissionError(13, 'Access is denied')`), leaving bootloader/partitions
written and the app half-written → the board boot-looped (`rst:0x3 SW_RESET`).

What made recovery work, and is worth reusing on a boot-looping CYD:

1. The COM port moved (COM6 → COM3) during re-enumeration — always re-detect the
   CH340 port rather than assuming the previous one.
2. Only the **app** needs rewriting once bootloader/partitions/boot_app0 verify,
   and it must be written with `--after no-reset` so the chip **stays in the
   bootloader** between retries; `--after hard-reset` drops it back into the
   broken app and every retry then fails with `Wrong boot mode 0x13`.
3. `esptool ... write-flash 0x10000 firmware.bin` succeeded on the first such
   attempt after the loop was restructured.

### Flash approach that worked first time

Written **image by image**, each with its own retry and all using
`--after no-reset` so the chip stayed in the bootloader throughout:

```
bootloader  0x1000   OK
partitions  0x8000   OK
boot_app0   0xe000   OK
app         0x10000  OK
then --after hard-reset
```

This avoids the unit-4 failure mode: one combined `write-flash` gives up on the
whole sequence if the 1.2 MB app write stalls, whereas per-image writes keep
what already verified.

### USB enumeration was intermittent

On first plug-in this board appeared briefly as COM3 and vanished; Windows
reported no port and no failed/unknown USB device for several minutes. It later
enumerated on COM3 and stayed. Worth noting because the symptom looks like a
dead board: **poll for the port rather than concluding from a single check**, and
prefer a rear motherboard port over a front-panel port or hub.

### Unit 5 Wi-Fi: `LSKK_Lantai2` rejected the credentials

Requested network `LSKK_Lantai2` would not associate. Both passwords tried
(`1234567890`, then `lskk_12345`) failed the same way:

```
[wifi] applying 'LSKK_Lantai2'
Reason: 15 - 4WAY_HANDSHAKE_TIMEOUT   (repeating)
Reason: 2  - AUTH_EXPIRE
```

The AP **is** visible — association proceeds to the WPA2 4-way handshake, so the
SSID matches; a wrong SSID would report `NO_AP_FOUND`. `4WAY_HANDSHAKE_TIMEOUT`
means the PSK was rejected, but a WPA3/SAE-only AP, MAC filtering, or too weak a
signal produce the identical code.

Isolation test: the same board joined `routerkantor` (password `1234567890`)
immediately — MQTT online, registered, catalog loaded. **The board's Wi-Fi is
healthy**; the fault is specific to `LSKK_Lantai2`.

Consequence: the unit is currently stored on `routerkantor` so it is functional
and registered. When the correct `LSKK_Lantai2` secret is known:

```
wifi LSKK_Lantai2 <password>
save
```

If the AP turns out to be WPA3-only, the ESP32 Arduino core 2.x build here will
not join it regardless of the password, and the AP needs WPA2 (or mixed) mode.

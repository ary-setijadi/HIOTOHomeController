# Home Automation — Versions

## v1.0 (preserved)
- 5 lamp-switch sensors and 5 lamp actuators over MQTT.
- Controller (Go, AMQP) running on the Orange Pi with a **fixed 1:1** pairing
  (`SNS-SW-000X` -> `ACT-LMP-000X`), algorithm `switch-lamp`.
- Node.js monitor + supervisory override (CLI and browser UI).

Artifacts: `controller/`, `simulator/` (server.js, monitor.js, supervise.js,
sensor-switch.js, actuator-lamp.js), plus the deployed `/root/controller` on
the Pi.

## v2.0 (rule engine + dynamic devices)
Adds:
1. **Compounding rules** — a switch can drive many lamps.
2. **Dynamic switch creation** at runtime.
3. **Dynamic rule registration/removal**.

Artifacts: `controller-v2/` (deployed as `/root/controller-v2`),
`simulator/create-switch.js`, `simulator/register-rule.js`, upgraded browser UI.

## v3.0 (whole house: DI/DO + analog)
- Full device inventory for a 2-parents + 4-children house: switches, lamps,
  pump (+feedback), temperature/air-quality/water-flow sensors, ACs, purifier.
- Rule engine with conditions (`op`/`threshold`), **hysteresis**, **debounce**
  (`min_duration_ms`), `then`/`else`, and **priority** (higher wins, first-write
  wins within a tick). Manual override supersedes all.
- Browser UI on port 3003 (whole-house dashboard + rule management).

Artifacts: `v3.0/controller/` (deployed `/root/controller-v3`),
`v3.0/simulator/` (house.js, server.js).

## v4.0 (time/trigger rules)
- Adds **time** condition type: `mode:"trigger"` + `when:{type:"time",at:"HH:MM"}`
  fires `then` once on the rising edge (event semantics, not level), plus
  `from`/`to` daily windows.
- Controller deployed as `/root/controller-v4` + `home-controller.service`
  (systemd, `Restart=always`).
- Browser UI on port 3004.

Artifacts: `v4.0/controller/`, `v4.0/simulator/`.

## v5.0 (mutual TLS with per-device certificates) — current
- **mTLS everywhere**: broker requires a valid client certificate
  (`ssl_options.verify = verify_peer`, `fail_if_no_peer_cert = true`).
- **Per-device identity**: each device/service has its own certificate
  (`CN = serial_number`) — 26 devices + `controller` + `monitor` + `house`.
- Endpoints: AMQPS `5671` (controller), MQTTS `8883` (devices + UI), management
  HTTPS `15671`. Plaintext AMQP `5672` / MQTT `1883` are bound to loopback only.
- Controller v5 = v4 rule engine over **AMQPS** with the `controller` client cert
  (Go, `amqp.DialTLS`).
- Simulator v5 = whole-house over **MQTTS**, one TLS connection **per device**
  (26 connections, each with its own cert). Reconnect is jittered to avoid a
  synchronized TLS-handshake storm on the 512 MB Pi.
- UI v5 = `server.js` over **MQTTS** with the `monitor` cert (port 3005).

### Deployment
- Certificates: `/etc/rabbitmq/certs/` (generated by `v5.0/gen-certs.sh`).
- Broker config: `/etc/rabbitmq/rabbitmq.conf` (see `v5.0/rabbitmq-mtls.conf`;
  backup at `/etc/rabbitmq/rabbitmq.conf.bak-plaintext-v4`).
- Controller: `/root/controller-v5` + `/etc/systemd/system/home-controller-v5.service`.
- Traffic logger: `/root/traffic-logger` + `traffic-logger.service` — subscribes to
  `home.#` over AMQPS and appends every message to a rolling **100 MB** file at
  `/var/lib/homeautomation/traffic.log` (keeps the newest 80 MB on rotate). It
  serves a query API on `:8080` (`/tail?bytes=N`, `/stats`); the dashboard loads
  only the most recent ~10 MB (10%) into memory and pages older history from this file.
- Clients keep only their own `<id>.crt`/`key` + shared `ca.crt` (PC copies in
  `v5.0/certs/`).
- Device manager: `/root/device-manager` + `device-manager.service` — registers
  devices, issues each a client cert (CN = serial) signed by the CA, and serves
  QR codes (`qrencode`) + an enroll API on `:8081` (`/api/register`,
  `/api/devices`, `/api/enroll/<serial>`, `/api/devices/<serial>/qr.png`).
- Registration app: `node server.js` in `v5.0/registration` (port `:3007`) — a
  camera page (`jsQR`) scans the QR and enrolls the device (saves cert under
  `v5.0/certs/`).

### Operational notes (recovery, 2026-09-16)
- RabbitMQ outage root cause was **hostname resolution**: `/etc/hosts` had no
  `maincontroller` entry, so `rabbit@maincontroller` resolved to an IPv6
  link-local address and the Erlang distribution listener (25672) failed.
  Fix: added `127.0.0.1 maincontroller` to `/etc/hosts`.
- The Mnesia reset (done during recovery) wiped the `admin` user; it was
  recreated with administrator tag + full `/` permissions.
- RabbitMQ 3.8.3 caveats: MQTT shares the top-level `ssl_options` (there is no
  `mqtt.ssl_options.*`), and the `none` listener value is not accepted (use
  loopback binding `127.0.0.1:<port>` to restrict plaintext instead).

### Operational notes (TLS hardening, 2026-09-23)
- **AMQP TLS 5671 is live** on the V4m broker: `listeners.ssl.default = 5671`
  plus top-level `ssl_options.*` (`verify_none`, `fail_if_no_peer_cert = false`).
  Verified: `openssl s_client` to 5671 presents `CN=maincontroller`.
- **MQTT TLS 8883 is deferred.** Adding `mqtt.listeners.ssl.default = 8883`
  (with the shared top-level `ssl_options`) makes a TLS MQTT client crash the
  processor: `rabbit_mqtt_processor:initial_state {error,einval}`. Legacy devices
  therefore stay on plaintext **1883**; the datacenter agent uses AMQP 5671.
- **Controller now auto-reconnects AMQP.** The connection was extracted into
  `v4m/controller/broker.go` (`connectOnce` re-declares exchange/queue/bindings/
  consumer; `watch` reconnects on `NotifyClose`). It survives RabbitMQ restarts
  instead of wedging on a stale channel.
